# 试销官 PRD

> 产品代号：试销官
> 产品形态：AI Agent 驱动的新品快反决策与实验工具
> 目标赛道：人工智能体（AI Agent）赛道——AI Agent × 鞋服产业
> 文档版本：v0.2（2026-09-03 MVP 决策冻结）
> 当前阶段：比赛 Demo / MVP
> 目标用户：永嘉中小鞋服企业及为其提供服务的 AI+OPC 运营者

## 1. 产品摘要

“试销官”是一款面向永嘉中小鞋服企业的新品快反决策与实验 Agent。

它接收新品候选款、产品 Brief 和经营约束，自主拆解需要验证的商业假设，生成低成本试销实验计划；在用户确认后，对可追溯的试销观测完成数据质量检查、证据分析和风险判断，输出 `Go / Pivot / No-Go / Evidence Insufficient` 四种结果，并仅在符合审批门禁时生成 TechPack Lite、打样任务或首单建议草稿。当前比赛 Demo 只使用预置场景控制台的每日聚合 `SYNTHETIC` 数据；企业授权数据接入是后续能力。

MVP 不试图“预测爆款”，也不承诺 90%—95% 的新品预测准确率。产品价值是把原本依赖经验、多人沟通和零散表格完成的新品决策流程，转变为一套可验证、可解释、可复盘的证据闭环。

## 2. 背景与第一性问题

本项目以主办方给出的永嘉鞋服产业痛点为第一事实来源：

- 款式迭代慢；
- 设计研发效率低；
- 供应链协同繁琐；
- 私域运营人力成本高；
- 客户需求响应滞后；
- 柔性生产适配不足。

网络公开资料、行业案例和竞品信息仅用于补充产品设计，不用于替代主办方对永嘉产业现状的定义。赛事方或企业后续提供的真实数据，应经过授权、验证和版本记录后再进入系统。

上述痛点背后的核心决策问题是：

> 在缺少充分历史数据、市场变化快且打样和生产存在实际成本的情况下，企业如何尽早判断一个新品候选款应当继续、修改、停止，或者补充更多证据？

现有工具往往分别解决设计、趋势、内容、销售、库存或生产问题，但中小企业仍需要人工完成以下连接：

```text
候选款
→ 提出商业假设
→ 设计试销方案
→ 收集与整理数据
→ 判断是否值得推进
→ 把结论转成打样和首单任务
```

“试销官”首先解决这条链路中的决策断点。

## 3. 产品定位

### 3.1 一句话定位

面向永嘉中小鞋企的轻量化新品快反编排 Agent：将来源状态明确的试销证据转化为可审计的新品决策，并按审批门禁生成打样和首单草稿。

### 3.2 产品边界

“试销官”不是：

- 保证爆款的预测系统；
- 替代设计师、商品企划或企业经营者的全自动决策者；
- 通用 AI 绘图工具；
- ERP、MES、PLM 或完整供应链系统；
- 自动抓取抖音、小红书等平台受限数据的爬虫；
- 在未经人工确认的情况下自动下单、排产或发布营销内容的执行系统。

“试销官”是：

- 新品假设与试销实验的规划者；
- 授权数据的检查和证据分析者；
- 带不确定性说明的决策助手；
- 设计、营销、供应链和工厂系统之间的轻量编排层；
- AI+OPC 模式下可由一人操作、按单交付的新品决策工具。

### 3.3 核心差异

- 面向永嘉中小鞋企，而非只服务拥有完善数据中台的大型品牌；
- 从“低成本验证”出发，而非直接依赖大量历史销量预测；
- 输出可追溯证据，而非只给出黑盒分数；
- 将分析结果转成 TechPack Lite、打样任务和首单三点情景范围；
- 允许连接现有设计、商品、ERP、MES 和私域系统，不重复制造已有基础设施；
- 对证据不足的场景能够主动拒绝下结论。

## 4. 产品目标

### 4.1 MVP 目标

1. 用户能够在一个流程中完成从产品 Brief 到新品决策包的工作。
2. Agent 能自主识别待验证假设并生成结构化实验计划。
3. 系统能通过预置场景控制台加载固定随机种子、每日聚合的合成试销数据，并且始终显示数据状态。
4. 所有结论都能追溯到数据、规则和用户输入。
5. 系统在证据不足时输出“证据不足”，而不是强行预测。
6. 符合决策与审批门禁的结果能够转化为打样和首单草稿；不符合时明确拒绝生成。
7. 单个 AI+OPC 操作者能够独立完成一次演示和交付。

### 4.2 业务价值假设

- 缩短从候选款提出到形成初步决策的时间；
- 减少低价值款进入完整打样或生产环节；
- 降低人工汇总数据、撰写报告和跨部门传递信息的成本；
- 提升新品决策依据的一致性和可复盘性；
- 为后续连接设计、供应链、私域和客服 Agent 建立统一数据对象。

### 4.3 非目标

MVP 阶段不以以下事项作为交付目标：

- 训练鞋服行业基础模型；
- 建设完整商品库、面料库或版型库；
- 实现真实平台自动投放；
- 直接接管企业采购、排产和生产；
- 覆盖所有鞋服品类和所有生产工艺；
- 证明跨企业、跨品类的统一预测准确率；
- 建设完整多租户商业化 SaaS；
- 替代线下试穿、材料检测和工艺验证。

## 5. 目标用户

### 5.1 核心用户：中小鞋企经营者或商品负责人

特征：

- 需要决定哪些候选款值得继续投入；
- 数据分散在表格、电商后台、私域记录和人工反馈中；
- 缺少专职数据分析或商品算法团队；
- 关注打样成本、首单风险、交期和库存风险。

核心诉求：

> 在投入完整打样和批量生产之前，用有限预算尽快获得足够可信的市场证据。

### 5.2 重要用户：设计师或产品经理

核心诉求：

> 知道消费者究竟不接受款式本身，还是价格、配色、卖点或素材表达存在问题，并获得可执行的改款建议。

### 5.3 重要用户：生产或供应链负责人

核心诉求：

> 收到结构清晰、约束明确、风险已标注的打样任务和首单三点情景范围，减少反复沟通。

### 5.4 AI+OPC 操作者

现阶段可由一名 AI 产品经理或产业数字化服务者承担。

核心诉求：

> 借助 Agent 独立完成需求录入、实验规划、数据处理、决策报告和交付物生成，以单个 SKU 或单次试销项目进行轻量交付。

## 6. 用户待办任务（JTBD）

### JTBD 1：决定候选款是否值得继续

当我面对多个新品候选款且预算有限时，我希望快速获得有依据的推进优先级，以便将资源投入更有希望的款式。

### JTBD 2：定位问题并指导改款

当试销结果不理想时，我希望判断问题来自款式、配色、价格、目标人群还是内容表达，以便决定修改后复测还是终止。

### JTBD 3：把结论交给打样和生产

当一个款式通过验证后，我希望自动形成完整度可检查的打样任务和首单建议，以便减少跨部门重复解释。

### JTBD 4：向管理者解释决策

当我提出继续、修改或停止某个款式时，我希望展示数据来源、判断规则、不确定性和风险，以便决策可以被审核和复盘。

## 7. 核心概念

### 7.1 候选款

尚未正式批量生产、需要验证商业可行性的鞋服产品方案。可以包含图片、文本、材料、颜色、价格、成本和生产约束。

### 7.2 实验

针对一个或多个假设设计的低成本验证任务，例如：

- 同一款式不同配色的点击或询单差异；
- 不同价格带的预订意愿；
- 不同目标人群的收藏或加购差异；
- 不同卖点表达对转化的影响；
- 候选款相对基准款的表现。

P0 只负责生成实验方案并分析预置场景结果，不直接控制外部平台投放；授权结果导入属于 P1。

### 7.3 证据卡（Evidence Card）

包含数据来源、数据质量、核心指标、对照结果、风险、反例和不确定性的结构化分析对象。

### 7.4 决策卡（Decision Card）

系统对一个候选款给出的结构化建议：

- `Go`：证据支持继续进入下一阶段；
- `Pivot`：存在可定位、可修改的问题，建议修改后复测；
- `No-Go`：在当前目标和约束下，不建议继续投入；
- `Evidence Insufficient`：数据量、质量或实验设计不足，不能可靠判断。

### 7.5 TechPack Lite

用于 Demo 和前期打样沟通的轻量化技术资料，不等同于完整工业技术包。它包含已知产品信息、需要确认的信息、关键尺寸或部件字段、材料方向、颜色尺码、成本和交期约束等。

## 8. 核心用户旅程

```text
创建男士轻量休闲鞋决策任务
→ 输入 1 个基础款、2 个配色变体与经营约束
→ Agent 识别待验证假设
→ Agent 生成实验方案
→ 人工审核并确认
→ 预置场景控制台运行或回放合成试销场景
→ 加载固定种子、每日聚合的观测数据
→ 系统检查数据质量
→ 应用确定性服务计算指标、形成证据卡并判定四态结果
→ Agent 仅对已锁定的证据与原因码生成引用式解释
→ 人工审批决策
→ Pivot 时生成并审批精确 PivotRevision
→ 人工确认绑定当前 Brief 版本的首单假设
→ 按决策门禁生成或拒绝生成 TechPack Lite、打样任务和首单三点情景
→ 导出决策包并保留审计记录
```

P0 实现四个独立人工门禁，审批均绑定目标对象 ID 与精确 `object_version`：

1. `EXPERIMENT_PLAN`：实验方案执行前；
2. `DECISION`：DecisionCard 生效前；
3. `PIVOT_REVISION`：仅 Pivot 路径，在改款交接前批准具体修订版本；
4. `FIRST_ORDER_ASSUMPTIONS`：首单情景计算前，确认意向转订单率、计划触达量和包装步长提案；目标绑定当前 Brief 版本并记录操作者和时间。

核心业务状态使用三个正交维度：`workflow_state` 表示流程位置，`quality_status=PASS/WARN/BLOCK` 表示数据质量，`decision_outcome=GO/PIVOT/NO_GO/EVIDENCE_INSUFFICIENT` 表示四种业务结果。审批作为不可覆盖的版本化 `Approval` 记录，不与这三类状态混用；详细契约见 `docs/DATA_DICTIONARY.md`。

### 8.1 P0 页面与门禁

| 路径 | 页面职责 | 关键门禁 |
| --- | --- | --- |
| `/` | 项目列表、Demo 场景选择、新建或重开任务 | 所有预置场景持续显示“合成演示” |
| `/projects/:id/brief` | 基础款、两个配色、人群、价格、成本、MOQ、预算、交期、图片与缺失项 | 可保存草稿；关键字段齐备才进入 `BRIEF_READY` |
| `/projects/:id/experiment` | 假设、唯一变量、实验臂、主/辅指标、样本、周期、停止规则、DemoPolicy 编辑与审批 | 批准后计划和阈值冻结；修改创建新版本 |
| `/projects/:id/simulation` | 场景选择、开始/暂停/逐日推进/重放、漏斗与预算进度 | 无自由调参；绑定固定场景、版本和种子 |
| `/projects/:id/evidence` | 数据质量问题、漏斗、配色对比、区间、支持/反对证据与限制 | `quality_status=BLOCK` 时不得产生 Go、Pivot 或 No-Go |
| `/projects/:id/decision` | 四态结果、原因码、规则命中、证据等级、风险、下一步与人工审批 | 服务端校验审批对象的精确版本 |
| `/projects/:id/handoff` | TechPack Lite、打样任务与条件式首单情景 | 仅已批准 Go 或已批准精确修订版本的 Pivot 进入；首单假设还需当前操作者针对当前 Brief 版本独立确认；严格执行产物矩阵 |
| `/projects/:id/audit` | 输入版本、场景/数据哈希、规则、Agent 运行/确定性服务审计、审批时间线与 HTML 报告 | 审计事件只追加、不覆盖 |

全局顶部固定显示 `data_origin`、`data_sensitivity_level`、在线/回放模式、`workflow_state` 和“非生产指令”。审批展示必须读取对象的 `approval_status` 或确认对象，不能仅凭 workflow 推断已批准。

## 9. 功能需求

### 9.1 P0：比赛 Demo 必须完成

#### P0-1 创建决策任务

用户可以创建项目并填写：

- 产品名称和候选款编号；
- 鞋/服品类；
- 目标人群；
- 使用场景和季节；
- 图片或款式描述；
- 核心卖点；
- 目标零售价；
- 预计成本；
- MOQ；
- 要求交期与供应商预计交期；
- 试销预算；
- 经营目标；
- 已知风险与限制。

Demo 种子项目固定为“男士轻量休闲鞋”，包含 1 个基础款和 2 个仅颜色不同的配色变体。数据层使用一个 `product_family_id`、一个基础 `candidate_id` 和两个 `variant_id`，不将配色变体冒充为三个独立候选款。

系统允许字段暂缺，但必须显示缺失项及其对决策的影响。

所有金额通过 Web 表单以元录入、按两位小数展示，提交时换算为整数分；前端拒绝超出 JavaScript 安全整数可换算范围的值，后端 `_fen` 字段拒绝超出 SQLite 64 位有符号整数上限的值。

创建项目时可只提交名称或不完整 Brief，此时 `workflow_state=DRAFT`；只有当完整负载通过 ProductBrief Schema 时才进入 `BRIEF_READY`。每次保存通过 `If-Match-Version` 锁定当前版本并创建新的不可覆盖版本。

任何未归档状态（包括已生成交接草稿）均可由用户显式新建 Brief 版本。该操作会根据新 Brief 的完整性回到 `DRAFT` 或 `BRIEF_READY`，停用当前数据集并清空当前计划、质检、指标、证据、决策和交接投影；旧观测、对象版本、审批和审计记录不删除。

#### P0-2 需求解析与假设生成

Agent 根据完整 Brief 生成：

- 用户需要回答的核心决策问题；
- 1—5 条可验证假设（内置 Demo 录制为 3 条）；
- 每条假设的关键指标；
- 可修改变量；
- 决策约束；
- 仍需用户补充的信息。

用户在 P0 可查看并确认结构化草案；如需改变输入或策略，创建新的 Brief/DemoPolicy 版本后重新生成计划。自由逐条编辑假设不属于当前实现。

#### P0-3 实验计划生成

Agent 输出结构化实验计划：

- 实验目标；
- 候选款和对照方案；
- 变量与保持不变的条件；
- 目标人群；
- 渠道；
- 核心指标和辅助指标；
- 建议预算、周期和样本量；
- 停止规则；
- 数据质量要求；
- 潜在偏差；
- 结果分别对应的后续动作。

首个 Demo 实验只允许一个主决策目标和一个实验变量：比较两个配色变体的购买意向率。价格、人群、渠道、素材、周期与卖点在该实验中保持不变；价格或卖点 Pivot 必须建立新的实验版本。

样本量只能表述为基于当前假设的建议，不得伪装为绝对科学结论。

实验计划必须由用户确认后进入下一状态。

已批准计划及其策略快照始终不可覆盖。如需改变 Brief 或 DemoPolicy，必须创建新版本并重开计划生成/审批链路，旧批准不自动对新计划生效。

#### P0-4 预置试销场景控制台

本轮 P0 不接受用户 CSV/Excel、手工观测数据或平台 API。控制台只支持：

- 选择预置黄金场景；
- 使用场景内固定的 `random_seed` 生成每日聚合试销观测；
- 开始短间隔的逐日自动播放、暂停、手动推进 1 天或直接运行至结束；暂停只停止前端计时器，不撤销服务端已写入的观测；
- 在决策批准或交接生成前重置并重放同一场景；重置将旧 `DatasetRecord.active` 置为 `false`（API 投影为 `DatasetSummary.active=false`），清除当前质检、指标、证据和未批准决策投影，但不删除观测、对象版本或审计记录；
- 展示 `scenario_id`、`generator_version`、`random_seed`、`schema_version` 和数据状态；
- 将数据快照固定到当次决策运行，便于审计和复现。

控制台不提供可以临时改变转化率、曝光、分流或经营约束的自由调参控件。要演示其他结果，必须选择另一个已版本化的预置场景。

P0 使用每日聚合粒度，一行唯一表示 `experiment_id + date + variant_id + channel + audience_segment`。最低字段与枚举以 `docs/DATA_DICTIONARY.md` 为唯一契约，包括曝光、点击、收藏、询单、加购、购买意向、价格、花费和数据来源字段。

所有试销观测强制标记为 `SYNTHETIC`，界面和导出强制显示“合成演示，仅验证流程与规则，不代表永嘉企业真实经营结果”。

来源限制必须由服务端执行：创建或更新 Brief 时提交非 `SYNTHETIC` 来源返回 `422`。候选款图片属于用户内容，上传后项目 `data_sensitivity_level=USER_CONTENT_RESTRICTED`，但试销 `data_origin` 仍为 `SYNTHETIC`。

#### P0-5 数据质量检查

系统对场景快照自动检查：

- 必填字段缺失；
- 数据类型错误；
- 重复记录；
- 漏斗指标逻辑异常；
- 样本量不足；
- 候选款或实验组不匹配；
- 时间范围异常；
- 明显极端值；
- 不同渠道口径不一致；
- 缺少基准或对照；
- 每个实验臂曝光是否至少 300；
- 每个实验臂购买意向是否至少 10；
- 在计划 50/50 分流下，Sample Ratio Mismatch 卡方检验是否出现 `p < 0.01`。

检查结果分为：

- 阻断性问题；
- 可继续但需警告的问题；
- 通过。

存在阻断性问题时，`quality_status=BLOCK`，且只允许输出 `EVIDENCE_INSUFFICIENT`；不允许输出 Go、Pivot 或 No-Go。

每个领域质检问题必须返回稳定 `issue_id`、`code/rule_code`、严重级别、受影响行/字段、记录引用、实际值 `observed`、预期值 `expected`、处理状态、消息和影响；请求 Schema 本身不合法时在进入质检前直接返回 `422`。

#### P0-6 证据分析

系统使用确定性计算工具完成指标计算，生成：

- 曝光到点击、收藏、询单、加购和购买意向的漏斗；
- 两个配色变体之间的差异；
- 两个配色在固定价格、人群、渠道和素材下的表现；
- 数据量和不确定性说明；
- 支持当前假设的证据；
- 反对当前假设的证据；
- 可能的混杂因素；
- 尚不能回答的问题。

每条证据陈述必须分别记录三个正交维度：`statement_type=OBSERVED/INFERRED/RECOMMENDED`、`inference_strength=CAUSAL/QUASI_EXPERIMENTAL/ASSOCIATIONAL/UNDETERMINED`、`evidence_grade=A/B/C/D`。观测事实不自动等于因果证据，模型文字不能作为新的独立证据。

大模型负责规划和解释，核心数值必须由程序计算，不允许由大模型估算。

#### P0-7 决策卡生成

每张决策卡至少包含：

- 决策结果；
- 一句话结论；
- 关键证据；
- 证据等级；
- 数据质量等级；
- 决策规则；
- 假设与限制；
- 主要风险；
- 下一步动作；
- 引用的数据记录或分析结果；
- 生成时间和版本。

决策规则必须可配置、可查看。相同输入数据和规则应产生相同类别结果，文字表述可以变化。

命中 Schema、样本、SRM、实验可比性等质量阻断条件时，系统必须输出 `Evidence Insufficient`；普通指标强弱或方向差异仍按已锁定策略确定性分支，不能由模型临时改判。

本轮默认使用 `DemoPolicy v1`，其值只是可测试的合成演示契约，不是行业基准：

- 主指标：`购买意向数 / 曝光数`；
- 数据门：每臂曝光≥300、每臂购买意向≥10；
- 分流门：计划 50/50，SRM 检验 `p<0.01` 则阻断强决策；
- 需求门：Go 要求两个实验臂购买意向率均≥3%；“相对提升≥15%”用于识别配色分化并进入 Pivot，不是 Go 的必要条件；
- 经营门：毛利率≥40%，`MOQ×单位成本≤首单预算`，交期满足 Brief 中的硬约束。

完整决策优先级、边界值和计算式见 `docs/DATA_DICTIONARY.md`。顺序为：质量阻断 → 冲突信号 → 明确低需求 No-Go → 不可修改约束 No-Go → 恰好一个可修改失败 Pivot → 全部通过 Go → 其他情况 Evidence Insufficient。明确低需求不能因轻微 MOQ/毛利/交期问题被升级为 Pivot；多个可修改失败也必须降级为 Evidence Insufficient。已批准实验内的策略快照永久锁定，Agent 和用户均不得覆盖；用户仍可在任何未归档状态提交当前 DemoPolicy 的新版本，但这会停用当前数据集、清空当前下游投影并回到 `DRAFT` 或 `BRIEF_READY`，必须重新生成和审批实验计划。

#### P0-8 Pivot 建议

当结果为 Pivot 时，系统必须指向 `DemoPolicy v1` 实际未通过的可修改门：

- 配色；
- 价格、材料或单位成本导致的毛利问题；
- MOQ 与首单预算冲突；
- 预计交期与上市窗口之间仍处于可协商范围的单一缺口。

目标人群、卖点、素材或款式细节只能作为后续实验假设，不能冒充当前配色实验已经验证的 Pivot 原因。每条建议必须关联证据或明确标记为待验证假设，不得凭空生成。

系统同时生成下一轮复测建议。

#### P0-9 TechPack Lite 与打样任务

字段契约为“通用鞋类字段＋男士轻量休闲鞋扩展”。交付物的生成必须遵守以下门禁：

- `GO`：决策获得人工批准且当前 Brief 版本的首单假设获具名确认后，可生成完整的 TechPack Lite 草稿和打样任务草稿；
- `PIVOT`：决策、精确修订版本和当前 Brief 首单假设均获批准后，只生成打样草稿，必须显示需要复测的修订点；
- `NO_GO` 与 `EVIDENCE_INSUFFICIENT`：不生成 TechPack Lite、打样任务或任何工厂交接包。

符合门禁时，系统生成：

- 产品基本信息；
- 产品图片或描述；
- 款式和部件信息；
- 材料方向；
- 颜色和尺码范围；
- 目标成本和零售价；
- MOQ 和交期要求；
- 试销结论；
- 待确认字段；
- 打样目标；
- 验收要点；
- 风险备注。

未知信息必须显示为“待确认”，不得自动虚构工艺参数。所有输出均为草稿，不等同于工厂已确认的工业 Tech Pack。

#### P0-10 首单建议

系统根据购买意向数据、成本、预算、MOQ 和已确认假设，输出：

- 保守、基准、进取三个首单场景；
- 每个场景一个按包装步长取整并受预算约束的离散数量点；
- 核心假设；
- MOQ 或预算冲突；
- 需要人工确认的条件。

三个离散点合在一起形成从保守到进取的条件式“首单情景范围”；单个点不是统计置信区间，也不是无条件可执行数量。界面和报告必须同时展示公式、假设、包装步长、预算约束和使用限制。

本轮不运行销量预测模型，所有预测类字段和评测指标显示 `N/A`。首单情景是由意向观测与经营约束推导的条件式建议，不是需求预测。`GO` 批准后可生成三情景草稿；`PIVOT` 必须先批准修订方案，且输出必须带“条件式首单建议—尚待复测，不得下单”水印；`NO_GO` 与 `EVIDENCE_INSUFFICIENT` 不产生首单建议。

情景锚点为 `购买意向数 × 已确认意向转订单率 × 计划触达量 / 模拟曝光量`；保守/基准/进取系数固定为 `0.8/1.0/1.2`。三个点分别按包装步长取整并受预算上限约束；预算上限或任一点低于 MOQ 时只返回冲突和 0 数量，不输出可执行量。

#### P0-11 报告导出与审计

支持导出或打印：

- 产品 Brief；
- 实验计划；
- 数据质量报告；
- 证据卡；
- 决策卡；
- TechPack Lite；
- 打样任务；
- 首单三点情景。

记录以下审计信息：

- 用户原始输入；
- 场景 ID、生成器版本、随机种子、数据快照哈希及摘要；
- 使用的规则版本；
- Agent 生成内容；
- 用户修改内容；
- 每次人工确认；
- 最终输出时间。

项目归档是受幂等保护的显式写操作，必须记录操作人和原因。`DECISION_APPROVED / HANDOFF_DRAFT_READY / CANCELLED` 可直接归档；其他活跃状态必须显式提交 `cancel_active_work=true`。归档不删除数据或版本，且 `ARCHIVED` 后禁止再修改 Brief 或 DemoPolicy。

## 10. Agent 行为要求

本轮只存在一个“试销官”逻辑编排 Agent 角色，不使用 handoff、子 Agent 或让模型持有业务状态。适配层可以为不同结构化输出调用创建短生命周期 SDK `Agent` 实例，这些运行仍属于同一逻辑角色，不等同于多个业务 Agent。

Agent 必须具备以下三类能力：

### 10.1 自主规划

能够把“这个款值不值得做”等模糊需求拆解为假设、实验、数据需求和决策步骤。

### 10.2 调用级只读工具

当前实现只有在线 `EXPLAIN_DECISION` 调用挂载一个工具：`read_locked_decision_evidence()`。它无参数，只返回应用在该次调用前锁定的 `fixed_outcome`、原因码、EvidenceClaim 和限制；不持有数据库会话、网络能力或写状态能力。该调用以命名 `tool_choice` 强制首次读取此工具，完成后由 SDK 恢复普通结构化输出；Brief 归一化与实验文字草案调用的 `tools=[]`，所有 SDK 调用的 `handoffs=[]`。

预置场景生成、数据校验、指标计算、四态规则、状态转换、审批、首单计算、交接和报告均由应用服务直接运行确定性代码，不是 Agent tools。未来连接器的权限和工具协议属于 P1，不能写成 P0 已实现能力。

### 10.3 场景定制

能够识别鞋服场景中的价格、材料、颜色尺码、MOQ、打样、交期等约束，并在信息不足时提出问题。

在线模式通过 DeepSeek 的 OpenAI 兼容 Responses API，默认使用 `deepseek-v4-flash` 和低推理强度；仅从 `DEEPSEEK_API_KEY` 取在线凭据，模型、Base URL、推理强度、超时和结构修复次数均使用 `DEEPSEEK_*` 环境变量配置。输出必须通过 Pydantic/JSON Schema 校验。离线模式只能按 `(input_sha256, prompt_version, output_schema_version)` 精确匹配固定录制，并在页面显示 `OFFLINE_REPLAY`；未命中返回 `422 REPLAY_RECORDING_MISS`，不得动态拼接或使用回放回答未录制的自由问题。

### 10.4 能力边界

Agent 必须：

- 区分事实、假设、推断和建议；
- 标明数据来源；
- 不虚构行业数据或工艺参数；
- 不将证据等级描述为预测准确率；
- 不将模型推断当作独立观测证据，模型文字不能提高证据等级；
- 不把相关性描述为因果关系；
- 对证据不足的场景拒绝强结论；
- 在外部发布、打样、采购和生产前等待人工批准。

## 11. 决策原则

### 11.1 决策不是单一模型分数

决策由以下因素共同形成：

- 实验设计质量；
- 数据质量；
- 样本充分程度；
- 核心指标表现；
- 相对基准；
- 经营约束；
- 证据一致性；
- 可修改空间；
- 生产与库存风险。

### 11.2 决策状态定义

**Go**

- 核心指标达到用户确认的门槛；
- 数据质量满足要求；
- 经营和生产约束未出现重大冲突；
- 不存在足以推翻结论的明显反向证据。

**Pivot**

- 当前方案未完全达到门槛；
- 证据与经营检查合计只能定位到恰好一个可修改变量；
- 修改成本和复测成本在可接受范围内。

多个可修改失败仍违反单变量 Pivot 合约，必须输出 `Evidence Insufficient`；明确低需求和不可修改约束直接进入 `No-Go`。

**No-Go**

- 数据质量足够；
- 在当前目标和约束下核心指标明显不达标；
- 未发现合理且低成本的修改路径，或生产约束使方案不可行。

**Evidence Insufficient**

- 样本不足；
- 关键字段缺失；
- 实验组不可比；
- 数据口径不一致；
- 指标相互矛盾；
- 缺少必要基准；
- 其他导致结论不可审计的问题。

### 11.3 证据等级

证据等级用于表达“当前决策依据的充分程度”，不得称为“准确率”。

建议分为：

- A：数据、设计和约束信息较完整；
- B：可用于方向性决策，但仍有明确限制；
- C：只能形成假设，建议补充实验；
- D：数据不可用或无法判断。

`SYNTHETIC` 数据的证据等级最高为 B、推断强度最高为 `ASSOCIATIONAL`；B 只表示对预注册、可复现流程与规则的范围受限方向性证据，不能支持真实市场需求或因果结论。`quality_status=BLOCK` 时证据等级为 D。

## 12. 数据假设

### 12.1 MVP 数据来源

本轮 P0 的试销观测只允许使用预置场景控制台生成的 `SYNTHETIC` 每日聚合数据。Product Brief 和审批意见可由用户填写，但不得将它们冒充为已授权的市场观测。

服务端在项目创建与每次 Brief 版本更新时拒绝非 `SYNTHETIC` 的 `data_status`。图片附件不改变观测来源；无附件时 `data_sensitivity_level=SYNTHETIC_ONLY`，存在用户图片时为 `USER_CONTENT_RESTRICTED`。

企业授权数据、主办方数据、公开样例和用户上传数据保留为 P1 输入类型；在完成授权、脱敏、字段映射与数据隔离前，不进入本轮 P0 流程。

不允许：

- 把网络传闻当作企业经营事实；
- 未经许可抓取受限平台数据；
- 使用来源和许可证不清的数据训练或展示；
- 将演示数据冒充永嘉鞋企真实数据；
- 在未脱敏情况下使用消费者个人信息。

### 12.2 冷启动假设

MVP 默认企业可能没有完整历史 SKU 数据。因此首版优先依赖：

- 当前候选款的结构化 Brief；
- 用户设定的经营约束；
- 小规模试销结果；
- 同一实验内的候选款或变量对比；
- 明确标识的专家规则。

历史相似款、预测模型和跨企业数据只能作为后续增强，不能成为 MVP 可用性的前提。

### 12.3 数据替换机制

演示数据、赛事数据和企业真实数据必须保持相同基础 Schema，使后续能够在不重写主流程的情况下替换数据源。

数据状态统一使用 `SYNTHETIC / PUBLIC_SAMPLE / USER_PROVIDED / ENTERPRISE_AUTHORIZED` 四种枚举，不另设含义重叠的“模拟”或“真实”布尔字段。当前 P0 只会产生 `SYNTHETIC`。

## 13. MVP 成功指标

### 13.1 产品流程指标

- 从创建任务到生成完整决策包，核心流程无需切换到外部表格进行人工计算；
- 一个单人操作者可以独立完成全流程；
- 所有 P0 输出物均可查看并导出；
- 关键步骤具有清晰状态和人工确认点。

### 13.2 质量指标

- 100% 的决策卡包含数据来源、决策规则、限制和下一步动作；
- 100% 的核心数值来自程序计算结果；
- 证据不足的数据能够被识别并阻止强结论；
- 同一数据和同一规则版本产生一致的决策类别；
- 未知工艺字段不被自动填充为虚构事实；
- 演示数据在界面和报告中始终明确标记。
- 本轮所有销量、爆款、概率预测指标显示 `N/A`，不以合成数据估计真实模型效果。

### 13.3 效率指标

Demo 阶段验证：

- 预置场景加载后，可在合理的演示等待时间内生成证据卡和决策卡；
- 相比手工整理表格和撰写报告，显著减少重复复制、计算和组织文本的步骤；
- 用户能够在一次连续操作中得到下一步打样和首单建议。

不在 MVP 阶段设定“预测准确率 90%—95%”目标。

### 13.4 后续真实评测指标

获得企业真实历史数据后，再评估：

- 决策覆盖率；
- Agent 拒答率；
- 决策校准度；
- 预测区间覆盖率；
- Go 款后续销售或动销表现；
- No-Go 款减少的无效打样投入；
- Pivot 后相对原方案的指标提升；
- 首单建议误差和库存风险；
- 人工接受、修改和否决比例；
- 单个 SKU 的决策时间和服务成本。

所有指标需要预先定义口径，并与简单基线比较。

## 14. P0 验收标准

### 14.1 输入与任务创建

- 可以创建、保存和重新打开至少一个新品决策任务；
- 只有名称或 Brief 不完整时项目停留 `DRAFT`，完整并通过 Schema 后才进入 `BRIEF_READY`；
- 必填信息缺失时有清晰提示；
- 可上传候选款图片或输入文字描述；
- 已知信息和待确认信息明确区分。
- 创建或保存 Brief 时伪装为非 `SYNTHETIC` 数据来源必须返回 `422`；上传用户图片只改变数据敏感级别，不改变试销来源。
- 在已批准计划、已分析或已生成交接草稿后保存新 Brief/DemoPolicy 版本，会停用当前数据集、清空当前下游投影并要求重新审批；历史版本、审批、观测与审计仍存在。
- 终态项目可归档；活跃项目未显式确认取消时归档返回 `409`，归档后 Brief 和 DemoPolicy 修改均返回 `409`。
- 归档后继续运行、推进或重置模拟也必须返回 `409`；界面不得从 workflow 单独推断审批已通过。

### 14.2 实验规划

- Agent 能从标准 Brief 生成结构化假设和实验方案；
- 用户可在批准前通过新 Brief 或 DemoPolicy 版本重新生成计划，并确认当前精确版本；当前实现不支持就地自由改写已生成计划；
- 未确认的计划不能标记为已执行；
- 计划包含指标、样本建议、风险和停止规则。

### 14.3 场景数据与校验

- 能选择、自动逐日播放、暂停、手动推进、重置和回放预置场景；暂停不撤销已写入观测，相同计划、场景版本与随机种子重放产生相同快照哈希；
- 重置后旧数据集不再活跃，旧观测、对象版本与审计事件仍可追溯；已批准决策或已生成交接物的项目重置请求必须被服务端拒绝；
- 界面不提供改写曝光、转化、分流等结果的自由调参入口；
- 缺失字段、重复数据、漏斗异常、每臂最小曝光/意向和 SRM 异常能被识别；
- 阻断性问题出现时系统只能输出 `EVIDENCE_INSUFFICIENT`，不生成 Go、Pivot 或 No-Go；
- `SYNTHETIC` 与“仅验证流程/规则”标识在界面和导出中不可遗漏。

### 14.4 证据与决策

- 系统能展示核心漏斗和候选款对比；
- 每条关键结论可以定位到数据或规则；
- 支持四类决策状态；
- 证据不足案例能正确进入 `Evidence Insufficient`；
- 同一输入和规则重复运行时决策类别一致。

### 14.5 下游交付物

- 仅已批准 Go 且已确认当前 Brief 版本首单假设时可生成完整 TechPack Lite 草稿；已批准精确修订版本并完成同一首单假设确认的 Pivot 只可生成打样草稿；
- 缺失工艺信息显示为“待确认”；
- 能生成结构化打样任务；
- 已批准 Go 能输出保守、基准、进取三个首单场景；Pivot 的输出具有不可忽略的条件式水印；
- No-Go 与 Evidence Insufficient 无任何 TechPack、打样或首单交接物；
- 所有生产相关建议在人工确认前处于草稿状态。

### 14.6 审计与导出

- 能看到输入、数据、规则和用户确认记录；
- 能生成一份完整决策报告；
- 报告不得包含“保证爆款”“95%准确率”“全球首创”等未经验证表述。

## 15. 风险与应对

### 15.1 冷启动和样本不足

风险：新品缺少历史数据，小规模试销可能产生高波动。

应对：

- 以实验和相对比较为主；
- 输出区间和证据等级；
- 支持证据不足状态；
- 后续使用企业历史相似款增强，不提前承诺。

### 15.2 渠道偏差

风险：单一平台、素材或受众导致结果不能代表真实市场。

应对：

- 保存渠道和人群字段；
- 在证据卡中暴露偏差；
- 不跨渠道直接合并不同口径数据；
- 建议必要的复测。

### 15.3 把相关性误当因果

风险：销售差异可能由价格、流量、人群或时间造成。

应对：

- 强制记录实验变量和对照；
- 展示混杂因素；
- 非随机实验只输出方向性结论；
- 后续引入因果评估工具。

### 15.4 大模型幻觉

风险：Agent 虚构数据、工艺参数或决策原因。

应对：

- 数值由确定性工具计算；
- 输出采用结构化 Schema；
- 结论强制绑定证据；
- 未知信息保留为待确认；
- 对关键输出执行规则校验。

### 15.5 数据与隐私合规

风险：企业数据、消费者信息或平台数据未经授权。

应对：

- 只接收授权和脱敏数据；
- 保存来源和授权状态；
- MVP 尽量使用聚合数据；
- 不采集无关个人信息；
- 导出前提供敏感信息检查。

### 15.6 知识产权风险

风险：候选款图片、设计或公开素材存在权利问题。

应对：

- 用户确认素材权属；
- 保存来源；
- 不将第三方设计用于无授权训练；
- Demo 优先使用自制或授权素材。

### 15.7 自动执行风险

风险：错误结论被直接用于采购或生产。

应对：

- 设置人工审批；
- P0 不提供自动下单和自动排产；
- 首单和打样输出始终为建议或草稿；
- 保留修改记录。

### 15.8 项目范围膨胀

风险：同时建设设计、营销、客服、ERP 和供应链系统，导致单人无法完成。

应对：

- MVP 固定在“实验—证据—决策—打样任务”闭环；
- 其他能力通过接口占位；
- 优先复用成熟模型和基础设施。

## 16. AI+OPC 交付模式

### 16.1 单人工作流

一名操作者可以完成：

1. 与企业确认候选款和经营目标；
2. 使用 Agent 生成并调整实验方案；
3. 在预置场景控制台运行或回放每日聚合合成数据；
4. 自动生成证据与决策包；
5. 与企业负责人确认；
6. 按决策与审批门禁输出、降级或拒绝生成打样/首单草稿；
7. 通过固定场景重放复盘数据、规则、模型模式和人工修改。

### 16.2 可行的商业化单元

MVP 阶段按一个候选款或一次试销项目形成最小交付单元。后续可探索：

- 按 SKU/试销任务收费；
- 月度订阅；
- 企业数据接入与流程配置服务；
- 工厂和系统适配服务；
- 真实成效验证后的增值决策服务。

PRD 不预设未经验证的定价和收入结论。

## 17. Demo 脚本

建议时长：6—8 分钟。

### 场景

一家匿名化的永嘉中小鞋企准备推出一款男士轻量休闲鞋，系统中记录 1 个基础款和 2 个配色变体。首个实验只验证配色，价格、人群、渠道、素材和卖点保持不变。演示使用明确标注的合成试销数据，不声称代表真实永嘉企业表现。

### 演示步骤

**第 1 步：创建决策任务**

输入产品 Brief、候选配色、目标人群、目标价格、成本、MOQ、预算和交期。

展示重点：系统理解的不是一句泛化问题，而是带经营和生产约束的新品任务。

**第 2 步：Agent 自主规划**

Agent 拆解假设：

- 用户是否偏好配色 A；
- 配色 A 的购买意向率是否达到绝对门槛且相对配色 B 达到提升门槛；
- 毛利、MOQ 预算和交期约束是否允许继续；
- 当前证据是否足以进入打样。

系统生成实验组、指标、样本建议、预算、风险和停止条件。

展示人工确认实验方案。

**第 3 步：运行预置试销场景**

在控制台选择预置场景，展示场景 ID、生成器版本、固定随机种子和 `SYNTHETIC` 标识，然后生成每日聚合数据。

先创建并运行 `INVALID_EXPERIMENT` 项目，使系统因每臂样本不足或 SRM `p<0.01` 输出 `Evidence Insufficient`；再从首页的另一预置场景新建项目继续演示。场景绑定在项目上，重放重置只会使用同一场景和种子；控制台不允许直接改写数据。

展示重点：Agent 不会无条件接受数据并生成漂亮结论。

**第 4 步：生成证据卡**

展示：

- 两个配色的核心漏斗；
- 配色 A/B 在相同价格、人群、渠道和素材条件下的表现；
- 支持证据和反向证据；
- 数据质量和不确定性；
- 可追溯的数据引用。

**第 5 步：输出决策卡**

以 `PIVOT_DESIGN` 为例输出 Pivot：

- 保留鞋款主体；
- 优先采用表现较强的配色；
- 只修订较弱配色并新建版本复测，不在同一 PivotRevision 中混入价格、MOQ 或交期改动；
- 当前不建议直接进入大货；
- 由于数据为合成演示，决策证据等级最高为 B、推断强度最高为相关性，而非宣称已验证真实市场效果、因果提升或高准确率。

**第 6 步：生成下游任务**

人工先批准当前 DecisionCard，再审批其精确 PivotRevision ID/版本，并由具名操作者确认绑定当前 Brief 版本的首单假设。三个门禁全部通过后，系统只生成：

- 带待确认材料和工艺字段的打样草稿；
- 下一轮复测计划；
- 带“尚待复测，不得下单”水印的条件式首单场景。

同时展示：若决策为已批准 Go，才生成完整 TechPack Lite 草稿；No-Go 和 Evidence Insufficient 始终无工厂交接物。

**第 7 步：展示审计与未来连接**

展示数据来源、规则版本、人工确认和最终输出。

最后说明未来可以连接：

```text
智能设计 Agent
→ 试销官
→ 营销/私域 Agent
→ 柔性供应链 Agent
→ 工厂 ERP/MES
→ 客服与售后反馈
→ 回流新品决策
```

强调“试销官”是决策编排核心，而不是在 Demo 阶段伪装成已经完成的全行业自动化系统。

## 18. Demo 准备清单

- 1 个结构完整的示例产品 Brief；
- 1 个基础款和 2 个配色变体；
- 1 个有效的固定种子预置场景；
- 1 个因样本或 SRM 问题必然进入 Evidence Insufficient 的预置场景；
- 1 个 Pivot 示例；
- 1 个 Evidence Insufficient 示例；
- 可查看、批准前可版本化修改、批准后锁定的 `DemoPolicy v1`；
- TechPack Lite 和打样任务模板；
- 三种首单情景模板；
- 完整决策报告；
- 清晰的“合成演示数据”标识；
- 网络或模型不可用时的固定演示回退方案。

## 19. 开发优先顺序

### 第一阶段：可跑通的单任务闭环

```text
Brief
→ Experiment Plan
→ Preset Scenario Console
→ Daily Aggregate Snapshot
→ Evidence Card
→ Four-outcome Decision Card
→ Decision Approval
→ PivotRevision Approval（仅 Pivot）
→ First-order Assumptions Approval
→ Gated Factory Handoff
```

### 第二阶段：可靠性加固

- 更完整的数据校验失败矩阵；
- 策略版本对比与迁移；
- 证据引用完整性加固；
- 人工审批边界和版本化回归测试；
- 审计检索与导出加固；
- 异常、拒答和离线未命中状态加固。

第一阶段已必须包含最小数据校验、人工审批、审计记录和 Evidence Insufficient 分支；第二阶段只是加固，不得把这些安全门延后到闭环之后。

### 第三阶段：展示与产业适配

- 鞋类字段；
- 决策报告；
- 打样任务；
- 未来系统接口占位；
- 比赛 Demo 和讲解材料。

## 20. 待验证事项

以下问题不能在缺少真实企业数据时预先假定答案：

- 永嘉企业最常用的试销渠道和数据导出格式；
- 不同鞋类品类的核心验证指标；
- 企业可接受的试销周期和预算；
- 打样任务的标准字段；
- 鞋楦、大底、材料和工艺数据如何编码；
- 企业现有 ERP、MES 或表格流程；
- 企业对四种 `decision_outcome` 的业务门槛，以及 Evidence Insufficient 质量阻断标准的实际偏好；
- 首单建议需要细化到何种颜色尺码层级；
- 企业愿意提供和持续回写哪些真实结果；
- AI+OPC 服务按 SKU、项目或订阅收费更合适。

这些问题应在赛事方提供数据或接触真实鞋企后，通过访谈、数据审计和小规模试点补齐，并记录到后续版本决策中。
